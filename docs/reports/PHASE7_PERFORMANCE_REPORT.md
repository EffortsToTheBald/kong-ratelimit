## 3. 测试版本与口径

- **被测实现**：Phase 6 冻结版（HEAD `7db6773`）。batch=1 走 EVALSHA token_bucket（每请求一次）；batch=10 走 GRANT_LEASE + Worker 本地 TAKE；多规则走 GRANT_MULTI。审计确认：**EVAL=0、SCRIPT_LOAD=0 全程（87 组）** ⇒ 无 legacy EVAL 路径残留、无 shared-dict 残留、无脚本缓存失效。
- **授权路径真实验证**：见 §13 账目核对（EVALSHA 数 == 请求数/GRANT 数，与代码路径一一对应）。
- **日志口径**：KONG_LOG_LEVEL=notice（与 Phase 1 Legacy 表格同口径）；[RL-DEBUG] 日志两代实现均存在，属同口径因素。

## 4. 测试方法

复用仓库现有 `bench/matrix.sh`（Phase 1 基线原装框架：逐 case 独立 namespace 配置下发 → k6 压 20s → 前后差值采集），仅做两处框架级扩展（非生产代码）：

2. 修正结果表打印模板输出第 20 字段（attempt；本轮 6 次运行的 md 中 attempt 列缺失，可由 k6 原始 json 文件名 `-a<N>` 恢复）。

- 每组：独立 ns（p4-*）→ 配置下发 → snap（Redis commandstats/cpu、Kong 日志行数、cgroup cpu.stat）→ k6 20s → snap → 差值入行。
- **污染判据**（沿用 Phase 1）：p99>500ms 或实测 RPS<95% 目标 ⇒ 重跑至多 3 次；被污染的轮次**保留原始数据**（本报告按 p99<500 过滤出"干净轮"求均值，污染轮在 §7 单列）。

## 9. batch=1 与 batch=10 对比

- **授权命令**：20001 → 2002，**约 9.99:1，约减少 10 倍**；与理论 1/batch 的微小差异来自多 Worker 独立预授权与批次边界（各 Worker 池耗尽时刻不同步，部分请求落在批次边界）
- **Redis 总 QPS**：4773 → 869（w2，**5.5×**；含连接建立/AUTH/SELECT 等非授权命令，故低于 10×）
- **p50/p95**：0.66→0.50ms / 1.41→1.16ms（w2 @1000），w1 同向（0.62→0.47 / 1.30→1.14）——本地 TAKE 零 IO 路径更快
- **p99**：82.8 vs 87.1ms（w2）/ 95.1 vs 103.8ms（w1）——**未见改善**（见 §15 问题 2 分析）
- **Kong CPU**：0.348→0.269 核（w2，−23%）；Redis CPU：0.079→0.021s（−73%）
- **时序精度声明**：batch=10 是预授权模式——90% 请求由 Worker 本地库存消费（remaining 头=本地池余量），配额精度为 batch 粒度预扣 + 桶 refill，非逐请求实时全局一致；这不等于每个请求都在 Redis 实时扣减（如实说明，不夸大）。

## 11. P95/P99 对比

- p95：batch=10 优于 batch=1（1.16 vs 1.41ms @w2；1.14 vs 1.30 @w1）——本地 TAKE 零网络往返的直接收益。
- p99：**两模式均为 80–104ms 量级且 batch=10 略高/持平**。归因：p99 由尾部阻塞支配——本宿主机存在 ~4s 周期性环境噪声（Phase 1 已记录），干净轮 p99 仍含 80ms+ 尾部事件（M0 也有 12–25ms 尾部，Docker 网络/调度波动）；Redis 往返减少的收益（~0.2ms 级）被尾部事件淹没。**不能用平均值证明提升，也不能用 p99 否认收益**：中位数与 p95 的改善 + Redis 资源占用下降是同口径下的可复现证据。
- 与 Legacy 对照（历史参考，环境不同不可严格比）：Legacy p99 b1=3.1/b10=2.2ms——当前宿主机噪声显著高于 Legacy 采集期（本轮 M0 p99=12.6ms vs Legacy M0=1.8ms），**不得据此声称实现退化**（M0 无限流也 elevated ⇒ 环境因素）。

## 12. Kong/Redis 资源使用

- Kong CPU（@1000，w2）：M0 0.225 → b1 0.348 → b10 0.269 → multi 0.341 核。b10 比 b1 低 23%（Redis 往返与 Lua 调用减少）；比 M0 高 20%（授权开销）。
- Redis CPU（@1000，w2）：b1 0.079s → b10 0.021s（−73%）；multi 0.101s（GRANT_MULTI 双键扣减开销高于单键）。
- Redis 内存：Lease 记录量级 ~万级 hash（TTL 1h），本轮压测窗口内内存占用可忽略（<10MB）。
- Worker 负载分布：w2 下 6 个 (host,worker) 均有 lease_grant 记录（见 §13）。

## 14. 性能瓶颈分析

1. **Redis 不是瓶颈**：b1 @1000 RedisCPU 仅 0.079s/20s（<0.5% 单核）；b10 降 73% 后 Redis 几乎空闲。
2. **Kong Worker 有余量**：0.27–0.35 核/三节点（20 核宿主机），RPS=1000 未触顶；RPS 恒定到达率下各模式均达标 ⇒ 吞吐瓶颈未达，提升空间未在本口径暴露。
3. **延迟底噪**：p50 0.45–0.66ms 由 Docker bridge 网络 + Kong 处理构成；p99 80–104ms 由宿主机环境噪声支配（M0 亦有 12–25ms 尾部）——精确归因需更干净的隔离环境（NOT VERIFIED）。
4. **GRANT 慢路径**：b10 中 10% 请求走 GRANT（~2ms 级 EVALSHA+本地登记），被 90% 本地路径摊薄，p95 反而低于 b1。

## 15. Lease 模式的收益与代价（问题 1–4 逐条回答）

**问题 1（Redis QPS 是否降低）**：是。授权命令 20001→2002，约 9.99:1（约减少 10 倍；与理论 1/batch 的微小差异来自多 Worker 独立预授权与批次边界），总 QPS 5.5×（含连接开销）。降低来源于本地库存消费（localHit 17998/20001 = 90%），经 §13 账目三源核对（EVALSHA/日志/Redis 记录），**不是请求丢失或错误放行**（200 数与消费数一致，429/5xx=0）。

**问题 2（P99 是否改善）**：p95 改善（1.41→1.16ms），p99 未改善（80–104ms 尾部由环境噪声支配，收益 ~0.2ms 级被淹没）。诚实结论：本环境下 p99 的因果归因 NOT VERIFIED，需要隔离环境重测。

**问题 3（吞吐是否提升）**：RPS=1000 到达率口径下所有模式均打满目标（无瓶颈暴露）；收益体现为资源占用（Redis CPU −73%、Kong CPU −23%）而非 RPS。更高压力下的吞吐拐点对比 NOT RUN（属环境容量外的加压测试）。

**问题 4（性能代价）**：存在，如实列出——① 预授权库存暂被单 Worker 占用：测试窗口结束时 7848（3.1%）授权总量与已消费量之间的未消费/未确认差额（不能全部认定为本地 outstanding；确认部分在 Worker 崩溃时即损失，Phase 6.5 实测 6/100）；② 授权时序精度：batch 粒度预扣 + refill，非逐请求实时一致；③ 本地库存形成短时突发消费（90% 请求零 Redis 延迟），突发特征与 batch 大小正相关；④ batch 越大，库存利用率损失敞口越大（本测试 3.1% 未消费/未确认差额即为例证，勿与 10% 的 GRANT 请求占比混淆——10% 是触发 GRANT 的请求比例，3.1% 才是授权库存的未消费/未确认差额比例）。

## 16. 测试限制与未覆盖场景

- **NOT VERIFIED**：p99 的精确因果归因（需无环境噪声的隔离宿主机）；Worker 崩溃对压测中途可用性的量化（Phase 6.5 已测正确性，未测性能影响）。
- **NOT RUN**：>1000 RPS 加压（避免超出宿主机承载失真）；>20s 长稳；Redis Cluster/主从切换下的性能；k6 分布式压测。
- **口径限制**：limit=1000000 隔离限流路径（与 Phase 1 同口径），429/拒绝路径性能未测；单规则仅 batch=10（未测 50/100——与本阶段核心问题无关，历史 B 组可参考 Legacy 趋势）。
- 环境噪声：**总执行 87 组 = 72 干净轮 + 15 污染轮**（p99≥500ms）；72 个 (模式×Worker×RPS) 组合中 60 个一轮通过、12 个触发重试（9 个重试 1 次、3 个重试 2 次，重试执行共 15 次，即 15 个污染轮）；**每模式 × Worker 配置 × RPS 档均有 3 个干净轮**（w2 r1/r2/r3 + w1 r1/r2/r3 各一，满足三轮有效数据要求），已保留全部原始数据并剔除于均值。

## 17. 结论

1. **同口径下，当前 Lease 实现确实大幅减少 Redis 授权交互**：授权命令 20001→2002（约 9.99:1，约减少 10 倍；与理论 1/batch 的微小差异来自多 Worker 独立预授权与批次边界），总 QPS 5.5×，Redis CPU −73%。
2. **延迟**：p50/p95 可复现改善（本地 TAKE 零 IO）；p99 受环境噪声支配未见改善，因果归因 NOT VERIFIED。
3. **吞吐**：到达率口径未暴露瓶颈；收益体现为资源占用下降。
4. **代价**：预授权导致 7848（3.1%）授权总量与已消费量之间的未消费/未确认差额（不能全部认定为本地 outstanding）与 batch 粒度时序精度，与 Phase 6.5 的正确性/损失语义一致。
5. 7.1 正确性 11 项：全部有既有 E2E 冻结证据（Phase 6.4/6.5 + 本阶段账目核对），映射表见 §13 与任务清单。
6. 7.3 协议矩阵核对：`test/lease-redis-matrix.sh` **50/50 PASS**（当前代码直接执行，非 smoke）。

## 18. 后续优化建议

1. 隔离环境重测 p99（消除 4s 噪声），补 RPS>1000 加压与长稳。
2. `_counters`（leases/tokens_granted/tokens_consumed/closed）已有基础，接 Prometheus 指标导出（Deferred，Phase 5+）。
3. lost 审计指标（granted−consumed−outstanding）以 Redis 记录 + 崩溃事件推导落表。
4. batch 自适应（auto 口径）与租户画像调参指南。
5. 多规则 GRANT_MULTI 的 Redis CPU（0.101s）高于单键，可评估多规则合并键或 pipeline 优化（不改语义）。
