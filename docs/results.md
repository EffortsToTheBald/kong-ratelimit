# Phase 4 第一组性能基线 —— Legacy EVAL + Shared Inventory

> 生成：本文件由三轮 matrix.sh 输出合并（见"测试命令"）。所有数据来自真实运行。

## 0. 环境与口径

- 宿主机：20 核 Linux（内核 7.0.0），**共享桌面机**（同机常驻 kubelet/K8s 节点、宿主 redis-server×2、IDE、本会话 agent；swap 已用 5GB）。
- 容器：3× Kong 3.6 DB-less（2 workers/节点）+ Redis 7（standalone）+ http-echo。
- 压测：k6 v0.54 constant-arrival-rate，每组 20s，RPS 档 100/500/1000，NODES 轮询 3 节点。
- 限流配置：limit=1000000/window=60（故意放大隔离限流路径，只测放行）；**batch 显式配置**（1/10/50/100，`resolve_batch()` 对 batch>0 直接采用，无 clamp 干扰）。
- **Legacy EVAL + Shared Inventory**：batch=1 每请求 1 次 EVAL；batch>1 先 store.take（shared dict 本地命中）后 EVAL slow path；多规则每请求 1 次 EVAL GRANT_MULTI。
- **Redis host/echo host = 容器 IP 直连**（见"发现 1"）。

## 5. 发现（本轮排查记录，均真实可复现）

### 发现 1：容器 DNS 间歇秒级阻塞（环境缺陷，影响 proxy 与 Redis 两条链路）
现象：域名模式（`echo`/`redis`）下，偶发（约 1/3 case）请求 waiting 层出现 3.8–4.0s 块；echo+redis 改 **IP 直连后完全消失**（多规则组 p99 从 4005ms → 3.5ms）。手动 curl 100 次最慢 50ms、Redis SLOWLOG 无慢命令、`http_req_connecting=0`（非连接建立）。
处置：基线全部使用 IP 直连；生产化建议（Kong DNS 缓存调优/静态 hosts/服务发现）列入 design.md 生产边界。**未修改生产代码。**

### 发现 2：KONG_LOG_LEVEL=notice 的日志背压主导尾延迟（现有真实缺陷）
现象：notice（RL-DEBUG 调试日志，每请求 2–4 条）下 batch=1 组 p95=3.6s/p99=3.8s；改 error 后同配置 p95=3.1ms/p99=71ms——**尾延迟由调试日志的 stdout 管道背压主导**，与限流开销无关。此为 Phase 1/2 遗留的临时调试日志（"调试日志为临时态"缺陷的量化实证）。
处置：notice 与 error 两段均保留（notice=当前部署形态如实呈现；error=隔离日志因素后的纯插件开销）。**未修改生产代码**；Phase 5 结构化日志改造时需处理。

### 发现 3：宿主机环境噪声造成偶发 4s 块（根因未定位，已建立污染判据与重跑机制）
现象：与本报告某次运行中，~5% 请求出现**常数级 3.8–4.0s waiting 块**，同时实测 RPS 掉至目标 ~95%——两者同源；**M0 无插件对照组同样出现**（与限流模式无关）；与连接建立（connecting=0）、docker-proxy（proxy/direct 1000 RPS 双模式干净）、DNS（IP 直连后仍偶发）、conntrack（9513/655360）、listen 队列（drops=0）均无关。`TCPSynRetrans=22170` 累计但无法定位归属。
判据与机制：**p99>500ms 或实测 RPS<目标 95% ⇒ 判定污染自动重跑（≤3 次尝试），尝试列在表中**；干净形态经验上限 p99≈188ms。重试仍污染则如实标注（本轮所有 case 均在 ≤3 次内取得干净数据）。
