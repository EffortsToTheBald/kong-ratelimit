# 实验协议：延迟 × 精度 × Redis 负载

> 目标不是"跑出好看的数"，而是**用同一份代码、一个参数，画出三条单调曲线**，
> 并给出取值的依据。评审看的不是你压到多少 QPS，而是你知不知道自己在上界附近哪里。

---

## 1. 控制变量

| 变量 | 固定值 | 说明 |
|---|---|---|
| Kong 副本数 | 3 | 客户轮询 8030/8010/8020 |
| worker 进程数 | 2 | `KONG_NGINX_WORKER_PROCESSES=2`，与 shared dict 行为相关 |
| Redis | 单实例，同宿主机 | 本机 RTT；跨机器的数字要另跑一轮 |
| upstream | `hashicorp/http-echo` | 极轻，避免上游噪声掩盖插件开销 |
| 时长 | 每组 ≥ 30s | 低于 30s 抖动大 |
| 到达模型 | constant-arrival-rate | 不要用 VU 循环，否则 RPS 随延迟漂移，无法比较 |

## 2. 四组实验

### E1 配额正确性（功能，不是性能）

```
limit=100, window=3600, batch=1
```

三节点各打 150 次（共 450），断言：

```
通过数 == 100          ← 必须严格相等
```

`window=3600` 是为了让"补充"在一分钟内可忽略，否则每秒补 1.67 个令牌会让结果不是整数。

### E2 少发上界（验证 4.3 的公式）

```
limit=100, window=3600, batch ∈ {1, 5, 20}
```

每个 batch 重复 5 次取通过数的均值，与理论下界对比：

```
预期通过数 ∈ [100 - 3*batch, 100]
```

### E3 延迟与吞吐（主实验）

```
limit=1000000（不触发限流）, window=60
rate ∈ {200, 1000, 3000} RPS
batch ∈ {基线, 1, 5, 20, auto}
```

注意把 limit 设得足够大，**让限流不介入**，否则你测到的是 429 路径而不是放行路径。

记录：`p50 / p95 / p99`、实际 RPS、错误率。

### E4 Redis 负载

在每组前后采样：

```bash
docker compose exec redis redis-cli INFO stats | grep total_commands_processed
```

差值 ÷ 时长 = Redis ops/s。预期：

```
ops/s ≈ RPS / batch
```

## 3. 一键跑

```bash
# 前置：docker compose up -d；k6 已安装（见 README 第 2 节）
cd kong-ratelimit
chmod +x bench/*.sh            # 从 Windows 拷过来时必做

./bench/matrix.sh -b 0,1,5,20 -r 200,1000 -d 30
```

脚本会：

1. 逐组 `POST /config` 到三个节点（顺带演示动态配置）
2. 等待配置生效（1s）
3. 记录 Redis `total_commands_processed`
4. 跑 k6，读 summary JSON
5. 输出 `bench/results.md`

## 5. 写结论时的三个"不要"

1. **不要**只贴数字不解释。每个数字要能对上一个机制（例如"p99 上升是因为 slow path 命中率 1/20"）。
2. **不要**隐瞒反常值。本机 Docker 网络下 `batch=1` 与 `batch=20` 的差值可能只有 0.1ms，
   看起来"优化没意义"——这时正确的结论是"本机 RTT 太小，收益被压缩；跨机房 RTT 1ms 时收益才显著"，
   而不是把数据藏起来。
3. **不要**把 `limit` 设得太大来做性能测试却不说明。评审会问"那你的限流到底有没有生效"，
   提前在文档里写清"E3 故意把配额放大以隔离限流路径"。

## 6. 复现性

- 记录 `docker compose` 版本、k6 版本、宿主机 CPU 核数。
- 每组跑 3 次取中位数；脚本默认 1 次，正式数据建议手动跑 3 次。
- 冷启动（容器刚起）的前 10s 有 JIT/连接池预热，不要计入。
